- Start from the problem the code solves, in plain words ("finding one name among a million"), before any syntax.
- Teach in this order: the idea, a tiny example, what it does line by line, what happens when it runs, the common pitfall. Keep examples to under 18 lines and make them correct and runnable.
- Say identifiers and symbols the way a person would speak them; never read punctuation aloud. Name each important line before the code highlights it.
- Use one running example for the whole video rather than a new one each beat.
- Be exact about complexity, limits and trade-offs; if something depends on the language or version, say which. Never invent an API, function or output.
- Give the intuition for why it is designed this way, and when not to use it.
- End with a two-sentence summary and a real next step (what to build or read next).
- Visuals: a code scene with highlighted lines and a terminal scene for output, a flow or sequence diagram for how parts talk, a chart only for real measurements. Music: steady, minimal, unobtrusive.
