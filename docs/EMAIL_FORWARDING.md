# Email forwarding for videomk.com

Mail sent to **hello@videomk.com** arrives in **chris@agilegency.com**. There is no mailbox at videomk.com: Amazon SES receives the mail, stores the raw message in a private S3 bucket (kept 7 days), and a small Lambda (`backend/lambdas/mail_forwarder.py`) sends a rewritten copy to the destination.

Code: `backend/mail_forward.py` (stack `videomk-mail`), `backend/lambdas/mail_forwarder.py`, `backend/lambdas/mail_activate.py`. Tests: `tests/test_mail_forwarder.py`, `tests/test_mail_cdk.py`.

## What gets created (prod account 464863885161, us-east-1)

DNS, in the existing hosted zone `Z07620702J1XHOWB4O7NZ` (no second zone):

| Name | Type | Value |
| --- | --- | --- |
| videomk.com | MX | `10 inbound-smtp.us-east-1.amazonaws.com` |
| videomk.com | TXT | `v=spf1 include:amazonses.com ~all` |
| _dmarc.videomk.com | TXT | `v=DMARC1; p=none; adkim=r; aspf=r` |
| three `<token>._domainkey.videomk.com` | CNAME | `<token>.dkim.amazonses.com` (EasyDKIM, generated by SES) |

Other resources: SES domain identity `videomk.com`; SES email identity for the destination; private SSE S3 bucket (block public access, SSL only, objects expire after 7 days, only SES from this account and this rule may write); receipt rule set `videomk-inbound` with one rule (`forward-hello`: recipient hello@videomk.com only, spam and virus scanning on, TLS required, actions S3 then Lambda by asynchronous invocation); the forwarder Lambda (Python 3.12, 256 MB, 60 s) with an SQS dead-letter queue and an alarm on it; a small custom resource that activates the rule set.

Existing records when this was designed: the zone has only the site's A/AAAA (apex and www), NS, SOA and the two ACM validation CNAMEs. There was no MX and no TXT at the apex, so nothing conflicts. If someone adds another apex TXT later (a site verification, say), put it in the same TXT record set with the SPF string; Route 53 allows only one TXT record set per name.

## Deploy

```
cd backend && PATH=/Users/chleiva/code/videomk/.venv/bin:$PATH AWS_PROFILE=default npx aws-cdk@latest deploy videomk-mail -c mail=1
```

Options: `-c forwardTo=<address>` (default chris@agilegency.com), `-c forwardFrom=<address>` (default hello@videomk.com), `-c mailReservedConcurrency=5` (see Risks).

SES allows one **active** receipt rule set per region. The deploy checks: if another set is active, the custom resource fails with a clear message and CloudFormation rolls back without touching it. If none is active (the state when this was written) or ours is, it activates `videomk-inbound`. On stack delete it deactivates only if ours is still the active one.

## Verify

1. The account is in the SES **sandbox**: SES sends only to verified addresses. Deploying creates the identity for the destination and SES emails a verification link to chris@agilegency.com. **The owner must click it once.** Production access is not needed for this single destination. Check: `aws sesv2 get-email-identity --email-identity chris@agilegency.com --region us-east-1 --query VerifiedForSendingStatus`.
2. The domain identity turns verified once the DKIM CNAMEs resolve (minutes): `aws sesv2 get-email-identity --email-identity videomk.com --region us-east-1 --query '{v:VerifiedForSendingStatus,d:DkimAttributes.Status}'`.
3. `aws ses describe-active-receipt-rule-set --region us-east-1` shows `videomk-inbound`.
4. Send a mail from another address (not the destination account's own alias) to hello@videomk.com. It should arrive within a minute as "<Sender> via videomk", Reply-To set to the sender.
5. Look at the log group `/aws/lambda/videomk-mail-forwarder` for `MAIL_FORWARD forwarded=1`.

## What the recipient sees (sender rewriting)

The copy is sent by videomk.com, not by the original sender, because forwarding a message as-is breaks SPF and DKIM and the original domain's DMARC policy would get it rejected. So:

* `From: "Ana via videomk" <hello@videomk.com>`; `Reply-To:` the original Reply-To, or the original sender; `To:` the destination.
* `X-Original-From`, `X-Original-To` and `X-Forwarded-By: videomk` are added; the original DKIM-Signature, Return-Path, Sender and Message-ID are removed (SES makes a new Message-ID). Subject, Date, body, attachments and charsets are kept (the MIME tree is not rebuilt by hand).
* Dropped, never delivered: SES spam or virus verdict FAIL, mail from hello@ itself or already marked `X-Forwarded-By` (loop guard), `Auto-Submitted` other than `no`, `Precedence: bulk|junk|list`, null return-path (bounces).
* Too large to send (about 9.5 MB after encoding; SES raw sending allows 10 MB): a short notice goes to the destination; the original stays in the bucket for 7 days (download it in the console).

**Limit:** pressing Reply in Gmail sends to the original sender, but *from chris@agilegency.com*, which exposes the personal address. To reply as hello@videomk.com, use the optional follow-up below.

## Optional: reply as hello@videomk.com from Gmail (Send mail as)

Needs SMTP credentials that only the owner creates (not part of the stack):

1. SES console (us-east-1) > SMTP settings > Create SMTP credentials. This creates an IAM user; save the SMTP user name and password (shown once). Restrict that user to `ses:SendRawEmail` with condition `ses:FromAddress = hello@videomk.com` if you want it tight.
2. Gmail > Settings > See all settings > Accounts and Import > Send mail as > Add another email address.
3. Name: videomk; email: hello@videomk.com; leave "Treat as an alias" checked. Next.
4. SMTP server `email-smtp.us-east-1.amazonaws.com`, port 587, TLS; user name and password from step 1. Add account.
5. Gmail sends a confirmation code to hello@videomk.com. It arrives through this forwarder (as "... via videomk"): copy the code or click the link.
6. Optionally set "When replying to a message, reply from the same address the message was sent to".

While the account is in the sandbox, SES delivers such replies only to verified addresses. To reply to anyone, request SES production access (SES console > Account dashboard); that is a separate decision.

## Change the destination

Redeploy with the new address (it sends a new verification mail, to be clicked): `... deploy videomk-mail -c mail=1 -c forwardTo=new@example.com`. Remember to pass the same `-c forwardFrom` if you changed it. The old destination identity is removed by the deploy.

## Add aliases (support@, privacy@) safely

The rule lists recipients exactly, so other addresses at videomk.com are rejected by SES at no cost. To add one: extend `recipients` of the single rule in `mail_forward.py` (keep one rule, keep scanning and TLS on), redeploy, and send a test. The Lambda forwards every recipient of the rule to the same destination, with `X-Original-To` telling which alias was used. Do not add a catch-all: it invites spam and costs money. Replies to an alias are sent as hello@videomk.com (the only sending address); add the alias to the `ses:FromAddress` condition only if you extend the Lambda to send from it.

## Roll back

* Stop receiving at once: `aws ses set-active-receipt-rule-set --region us-east-1` (no name = no active set; mail is then rejected by SES), or disable the rule: `aws ses update-receipt-rule ...` with Enabled false.
* Stop MX: delete the MX record in Route 53 (senders then see no mail host).
* Full removal: `npx aws-cdk@latest destroy videomk-mail -c mail=1`. The raw bucket is retained (delete it by hand when empty); the rule set is deactivated only if still ours.

## Tightening DMARC later

DMARC starts at `p=none` (monitor only, no reports are requested because there is no address of ours to receive them). Our mail is DKIM-signed by SES for videomk.com, so it aligns. After a few weeks of normal use, change `DMARC` in `mail_forward.py` to `p=quarantine`, later `p=reject`; add `rua=mailto:...` only to an address we control (hello@ itself would work: reports are dropped by the loop and auto-mail rules only if they carry those headers, so prefer a dedicated alias).

## Cost (rough)

SES inbound about $0.10 per 1000 messages plus $0.09 per 1000 chunks of 256 KB; outbound $0.10 per 1000; Lambda, S3 (7-day retention), SQS and logs are pennies for a mailbox of this size. The account may use SES for other things: this stack creates only its own identities and rule set and sets no account-level SES option.

## Monitoring

* `MAIL_FORWARD forwarded=1 kind=forwarded|too_large bytes=N id=<hash>`; `MAIL_FORWARD dropped=1 reason=spam|virus|loop|auto_submitted|bulk|null_return_path id=<hash>`; `MAIL_FORWARD_FAILED stage=event|read|send id=<hash>`. No address, subject or content is ever logged (the id is a short hash).
* A failure raises, so Lambda retries twice; after that the event goes to the SQS dead-letter queue (output `DeadLetterQueue`), where an alarm fires when anything is waiting. The original mail is still in S3 for 7 days: re-send by invoking the Lambda with the saved event, or forward it by hand.
* A metric filter on `MAIL_FORWARD_FAILED` can be added if more alarms are wanted.

## Risks and notes

* Sandbox limits: 200 messages per day, 1 per second. Plenty for a contact mailbox; throttles retry.
* The prod account's Lambda quota is 10 concurrent executions in total (checked read-only). AWS refuses a reservation that leaves fewer than 10 unreserved, so the forwarder has **no** reserved concurrency by default. SES delivers mail one message at a time per rule, so a flood is bounded by the sandbox rate. Raise the account quota, then deploy with `-c mailReservedConcurrency=5`.
* The destination keeps spam filtering of its own; the SES verdict drops only clear spam.
