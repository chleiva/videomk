# Languages: English and Spanish (policy, glossary, keys)

Decided 2026-11-26. English is the default; Spanish is a first-class language. When a person's device or browser is in Spanish, everything they see is Spanish: sign-in, every screen, errors, legal pages. This file is the contract for the server, the web and the iOS and Android apps.

> The language of a VIDEO is a separate matter from the language of the apps: a video can be made in more languages than the apps are translated into. See `docs/LANGUAGES.md` (2026-11-27: French, German, Italian, Portuguese, Dutch, Polish and Finnish videos, on for QA).

## Locale policy

* Supported locales: `en` (default) and `es`.
* **Selection order: the person's explicit choice in Settings > the device or browser language > English.**
* Any `es-*` (`es-ES`, `es-MX`, `es-419`, `es_AR`) maps to `es`; any `en-*` maps to `en`. Any other locale (`fr`, `pt-BR`, `zh-Hans`) falls back to English. Never guess a third language.
* The apps send the resolved locale (`en` or `es`) in the **`X-Locale` header on every API call** (contract in `docs/CREATE_API.md`, section "Language"). They do not send raw device locales and do not use a `lang` query parameter.
* The narration language of a video is a different choice (`language`: `auto`, `en`, `es`, see `docs/CREATE_API.md`); the engine already writes Spanish narration. The app language never changes what a video says, only the app and the server messages.
* Text written by the model (intake questions and option labels, `not_supported` message, titles, narration) follows the language of the person's request, not of the app. Do not translate it on the client.
* Machine values are never localized: ids, `code`, `status`, numbers, flags. Language names are written in their own language (`English`, `Español`) in both locales.
* Web: Spanish pages live at `/es/...` (static, with `hreflang` alternates, a visible English | Español switcher in the footer); English stays at `/`. App screens (signed in) have one URL and follow the saved choice (`localStorage` key `vmk_locale`) or `navigator.language`. The landing page at `/` sends a Spanish browser to `/es/`.

## Where the text lives

| What | File | Used by |
|---|---|---|
| Server messages, capabilities labels and notes | `backend/lambdas/common/i18n.py` (`EN`, `ES`) | every API handler (`t(key, locale, **params)`, `pick_locale(event)`) |
| Web app text | `frontend/src/i18n/en.json`, `es.json` | React components, Astro pages (`src/lib/i18n.ts`) |
| Legal pages | `frontend/src/data/legal/*.ts` (`*.es.ts` for Spanish) | `/privacy`, `/terms`, `/support`, `/delete-account` and their `/es/` twins |
| iOS | `Localizable.xcstrings` (String Catalog), one entry per key below | the iOS builders |
| Android | `res/values/strings.xml` and `res/values-es/strings.xml` | the Android builders |

`python backend/scripts/i18n_check.py` checks the server and web catalogs: same keys, same placeholder names, same plural forms (errors), plus warnings for Spanish text identical to English, text that looks untranslated, words the glossary avoids and text more than 1.8 times longer than English. `--strict` makes warnings fail. It runs in the backend test suite (`tests/test_i18n.py`). The native builders should run the same idea over their own catalogs.

## Key conventions (web, iOS and Android all follow them)

1. **Stable keys.** `area.name` in lower case with dots and underscores, named for the meaning, never for the English words: `gen.empty`, `signin.error`, `editor.publish_hint`. Never reuse a key for a different meaning; never rename a key to fix a typo in the text (change the text). Android maps dots to underscores (`gen_empty`); iOS uses the key as is.
2. **No concatenation.** One sentence is one key. Never build a sentence from pieces (`"Step " + n + " of " + total`); the word order differs between languages. If a link sits inside a sentence, give the sentence a placeholder for it (`"See our {terms} and {privacy}."`).
3. **Named placeholders** in braces: `{count}`, `{title}`, `{date}`. The same names in English and Spanish. On iOS use the catalog's named or positional equivalents (`%1$@`), on Android `%1$s`; the meaning of each placeholder is the same on every platform.
4. **Plurals use ICU** `{count, plural, one {# credit} other {# credits}}` (only `one` and `other` are needed for English and Spanish; `#` is the number). Native catalogs use the platform plural mechanism (xcstrings plural variations, Android `<plurals>`) with the same two forms. Zero is `other` in both languages: write the text so that it reads well for 0 ("0 créditos").
5. **No text baked into images or icons.** Accessibility labels are keys too.
6. **Do not translate** brand and product names (videomk, YouTube, TikTok, Instagram Reels, LinkedIn, X, Apple, Google), codes, file formats, `4K`, `720p`, `1080p`.
7. **Dates, times, numbers, durations** come from the platform formatter for the locale (`DateFormatter`, `Intl`, `DateUtils`), never from hand-written strings. Unit abbreviations in text: `s`, `min`, `h` (same in Spanish), written with a space before them in Spanish (`45 s`).
8. **Server text is shown as received** (`message`, capabilities `label` and `note`): the app does not translate or re-word it; it makes sure it sent `X-Locale`. After a language change the app refetches capabilities.
9. **Expansion.** Spanish is about 25% longer. Buttons and chips must wrap or grow; test at the largest text size in Spanish. Keep strings short.
10. Add a Spanish entry the moment you add an English one. A missing Spanish key shows English (never an empty label or a key), but it counts as a bug.

## Tone and style (Spanish)

* **Neutral international Spanish** that reads naturally in Spain and Latin America. **Tú** form, friendly, short, direct. Never "usted", no voseo (`tenés`), no slang.
* No regionalisms: say **teléfono** (not `móvil`, `celular`), **video** without accent (the RAE-accepted form, common in Latin America and now in Spain; never `vídeo`), **correo** for email, **archivo**, **foto**, **app**. Avoid `ordenador` and `computadora`: say "tu dispositivo" or "el navegador" if needed.
* Imperatives for actions: "Crear video", "Iniciar sesión", "Eliminar cuenta". Short labels in sentence case (Spanish does not use Title Case): "Mis videos", not "Mis Videos".
* Errors say what happened and what to do, kindly and briefly: "No pudimos cargar tus créditos. Inténtalo de nuevo." Do not blame the person; do not write "Error:" prefixes; do not use exclamation marks for problems.
* Safety stops (the most delicate text): kind, short, never name the rule or accuse: "No podemos crear este video. Si tenías otra idea en mente, prueba a describir una distinta."
* Punctuation: opening `¿` and `¡`, typographic quotes “ ”, a single ellipsis character `…`, `p. ej.` for "e.g.". Use "Entendido" rather than "OK" on a consent button; "Aceptar" only for a real confirmation.
* Verbs: `Agregar` for "Add" (neutral across regions), `Eliminar` for "Delete", `Descartar` for "Discard", `Iniciar sesión` / `Cerrar sesión`.
* Do not translate literally: "Just inspire me…" is "Sorpréndeme…", "pick up where you left off" is "retoma donde lo dejaste".

## How to add or change a string

1. Server: add the key to both `EN` and `ES` in `backend/lambdas/common/i18n.py`; use `i18n.t(key, locale, **params)` with `locale = i18n.pick_locale(event)`; for an error raised deep inside shared code, raise `i18n.Localized(key, **params)` and render it with `i18n.error_text(exc, locale)`. Add the English text to `ENGLISH_BEFORE` in `tests/test_i18n.py` (the golden English table).
2. Web: add the key to `frontend/src/i18n/en.json` and `es.json`; use `t(key, params)` from `useLocale()` in React or `data-i18n="key"` in Astro app pages.
3. Run `python backend/scripts/i18n_check.py` and the tests.

## What the owner should review

The web and server Spanish was written by an assistant: the owner (native Spanish speaker) reviews it. The legal pages are first drafts like the English ones; the English version prevails in case of conflict (stated at the foot of every legal page, in both languages).

## Known gaps

* Cognito's own verification emails (sent by the user pool) are the default English template: a custom message Lambda that reads the locale is not built yet. The hosted sign-in page itself follows `lang=es`.
* Titles, narration and the intake model's text follow the request language by design.
* Mobile apps are localized by their own builders after the account deletion UI lands; they use the keys and the header contract above.

## iOS decisions (2026-11-26)

* **One catalog, one function.** All app text lives in `mobile/ios/Packages/VideoMKCore/Sources/VideoMKCore/Strings/Localizable.xcstrings` (English source + Spanish, plural variations `one`/`other`) and is read with `tr("area.key", args...)` (`Localization.swift`). The catalog ships as a plain resource and is read directly, so the same code runs in the app and in `swift test` (SwiftPM does not compile catalogs). `VideoMK/InfoPlist.xcstrings` holds the display name and the microphone and speech permission texts. No `Text("literal")`: `scripts/check_literals.py` fails the build gate on literals.
* **Keys** are `area.short_name`; many were derived from the first words of the English text (e.g. `create.what_is_it_for`). The text may change, the key never does.
* **Selection order** is implemented as written: explicit choice (Settings > Language: Automatic, English, Español; stored in `UserDefaults` key `vmk_locale`) > device or per-app language (`Locale.preferredLanguages`) > English. A change applies at once, without a restart (the root view is rebuilt and capabilities are fetched again in the new language).
* **`X-Locale`** is sent by `APIClient` and by the account-deletion client on every call. Hosted sign-in gets no `lang` parameter yet.
* **Account deletion confirmation word**: `DELETE` in English, `ELIMINAR` in Spanish; either is accepted in either language (the request body still sends `DELETE`).
* Legal links in Spanish point to `https://videomk.com/es/privacy` and `/es/terms`.
* Spanish month abbreviations in suggested collection names are lower case with a dot-free form (`jul 2024`); group names from the server are read in either language.
* The photo-request detector (`PromptPhotoIntent`) also knows Spanish words (mis fotos, vacaciones, boda...).
